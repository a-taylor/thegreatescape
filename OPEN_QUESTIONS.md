`BUILD_PROMPT.md` §0: *"If something cannot be determined from the disassembly, do not guess
silently: record it in `OPEN_QUESTIONS.md` with the address you were reading, state the
assumption you are proceeding with, and mark the code `// ASSUMPTION:`."*

Entries 1–7 are places where **`BUILD_PROMPT.md` itself misstates its own source material** —

## 1. The disassembly does *not* contain the bfix/rfix corrections — `BUILD_PROMPT.md` §1 is wrong

**Status:** Resolved (brief is incorrect). The consequence — that each fix is now a deliberate
decision rather than something inherited — is discharged: all eight are enumerated with their
disposition in `FIDELITY.md`. One is applied, one is pending a clear §9 rule, five are inert,
and one (`$CCED`) is open for P5. **None block P4.**

**What I was reading:** `TheGreatEscape.skool` lines 13–32 (the `@ofix`/`@bfix`/`@rfix` header
blocks), then the three bfix sites at `$7CAF`, `$A2C6`, `$B935`.

**The brief says** (§1):

> the disassembly applies a small set of `@bfix`/`@rfix` corrections to the original code — a
> ROM-write fix at `$A2C6`, a mask iteration count fix in `render_mask_buffer`, a missing
> `RET`, an `is_item_discoverable` fix at `$CCED`, and some redundant-jump removals.
> **Implement the disassembly as written** (i.e. the corrected version).

**What is actually there:** there is no corrected version to implement. The file contains
**zero** `@bfix=`, `@rfix=`, `@ofix=`, `@ssub=` or `@rsub=` substitution directives. The
complete column-0 directive census is:

```
1174 @label     88 @nowarn     28 @keep     6 @isub     2 @assemble
   1 each: @writer @start @set-warnings @set-line-width @replace @org
   1 each: @ofix+begin @ofix+end @bfix+begin @bfix+end @rfix+begin @rfix+end
```

The six `+begin`/`+end` directives bracket **prose in the header comment**, nothing more. They
are SkoolKit's mechanism for including explanatory text in a fixed build; they carry no
alternative source lines. At the actual bug sites the **original, buggy bytes are encoded**,
with the problem noted only in a `; Bug:` prose comment (28 such comments exist):

| Site | Encoded in the `.skool` | The described fix |
|---|---|---|
| `$7CAF` | `RET Z` | `RET` — the conditional is needless |
| `$A2C6` | `LD B,$07` | `LD B,$06` — seven iterations over the six-entry `beds` array (`w$6B79`), causing the ROM write to `$1A42` |
| `$B935` | `LD B,$3B` (59) | 58 — `exterior_mask_data` (`$EC01`) is only 58 entries long |

This is expected once you know the build pipeline: the `.skool` is generated by
`sna2skool.py --ctl TheGreatEscape.ctl build/TheGreatEscape.pristine.z80` (Makefile line 53),
i.e. it is a rendering of the **pristine tape image**. Applying fixes is a `skool2asm --fixes`
option, not a property of the file.

**Assumption I am proceeding with:** implement the three bfixes and five rfixes **deliberately**,
derived from the header prose and the `; Bug:` comments, each with its own `FIDELITY.md` entry
and a `// ASSUMPTION:` marker at the call site. This matches §9's explicit instruction not to
reproduce "crashes, hangs or the ROM write", so the *intent* of §1 is preserved even though its
factual claim is not.

**Why this needs review:** §1 framed these as free — already applied upstream. They are not.
Each is now a small deliberate deviation from the encoded bytes, and §0 forbids silent
deviation. In particular the `$CCED` `is_item_discoverable` fix is described in the header as a
"potential bug fix" (line 30) and in `TheGreatEscapeBugs.ref` as an off-by-one at `$CCCD` where
`HL` is decremented but not restored — I will need to determine the exact corrected form from
the code rather than the prose.

## 2. Game window is 192×128, not 192×136 — `BUILD_PROMPT.md` §4

**Status:** Resolved. The brief anticipated this: *"verify the exact bounds from the disassembly
rather than trusting this sentence."*

**What I was reading:** `game_window_start_addresses` (`w$EDD3`), and the buffer note at
`TheGreatEscape.skool` lines 20374–20375.

The brief says the game window is "24×17 characters (192×136 px)". Both numbers appear in the
disassembly, but they describe **different things**:

| Thing | Address | Size |
|---|---|---|
| `tile_buf` (visible tiles array) | `$F0F8` | 24×17 = 408 bytes |
| `window_buf` (screen buffer) | `$F290` | 24×17×8 = 3,264 bytes → 192×136 px |
| **Visible window** | — | **192×128 px** |

`game_window_start_addresses` holds exactly **128** screen pointers (verified by count, and by
the block ending at `$EED3`). The first is `$4047`, which decodes to character column 7, pixel
row 16. So the buffer is 17 tile rows tall but only 16 are ever blitted — the extra row is
sub-tile scroll slack. `TheGreatEscapeGraphics.ref` line 235 independently confirms: *"the
192x128-sized viewport"*.

**Assumption:** buffers at 24×17; blit exactly 128 rows starting at column 7, row 16.

## 7. The PRNG range is not a table — §6

**Status:** Resolved.

§6 says to extract "the byte range at `$9000..$90FF` that `random_nibble` (`$CB85`) reads from…
extract that range verbatim; it is data, not a generator." Correct that it must be extracted
verbatim — but it is not a distinct table. `$9000..$90FF` lies **inside `exterior_tiles`**
(`$8590`–`$9768`, itself inside the giant `b$8218` block): the game reads exterior **tile
bitmap data** as its entropy source. The 256 bytes are lines 6348–6379 of the `.skool`, tagged
in comments as `exterior-tiles2-189` onward.

Two implementation details visible only in the code (`$CB85`–`$CB91`) that a paraphrase loses:

- `INC L` executes **before** the read, so the first value returned comes from `$9001`, not
  `$9000`, even though `prng_pointer` (`g$C41A`) is initialised to `$9000`.
- Only `L` is incremented — `H` is never touched — so it wraps within the `$90xx` page.

**Assumption:** extract as a raw address slice, and reproduce both details exactly.

## 8. `room-N.png` is not a valid pixel oracle — affects §7 P1 and §8

**Status:** Assumed (decision taken; recorded here because it changes an acceptance criterion).

**What I was reading:** `The-Great-Escape/TheGreatEscape.py:627` (`_render_room`).

§8 states the shipped PNGs "are a genuine oracle: render the same thing and compare
pixel-for-pixel", and §7 makes P1 conditional on *"rendered room N is pixel-identical to
`images/scr/room-N.png` for all rooms"*.

For rooms this does not hold. `_render_room` renders onto a hardcoded 24×16 canvas, carrying
the author's own comment:

```python
# room_dims is not comprehendible to me right now .. could use a
# worst-size case of the screen size
room_width, room_height = 24, 16
```

It ignores each room's `dimensions` and `boundaries` (both decoded but unused), forces attribute
7 for every tile via `_interior_tile()`, applies no masks, and draws no sprites, items or hero.
There is also **no capture of the running game anywhere** in the source material —
`static-images/GameWindow.png` is a hand-drawn annotated diagram, not a screenshot.

So matching `room-N.png` pixel-for-pixel would calibrate the renderer to a placeholder canvas
rather than to the original game.

**Assumption:** the golden-image gate is split by asset class. Pixel-exact comparison is kept
for everything produced by real byte→UDG decoding — `map-0-0.png` (the strongest oracle: the
whole 54×34 grid at 1:1, uncropped), the 876 individual tile PNGs, 218 supertiles, 51 RLE
objects, 30 scenery masks. Rooms are gated **structurally** (correct objects at correct `(x,y)`
from the roomdef), with full-frame fidelity deferred to P2 against the real display model.

**Also excluded from pixel comparison,** and worth recording so nobody wires them up later:

- Composited `<who>-<dir>-<n>.png` character frames — bitmap and mask merged with a green
  "transparent" colour, and `TheGreatEscapeGraphics.ref` line 38 states the masks are
  *"inaccurate and misshapen… 'worst case' ones shared between multiple frames to save space"*.
  Use the separate `bitmap-*.png` / `mask-*.png` instead.
- The unindexed `<who>-<dir>.png` files are **animated PNGs** (`acTL`/`fcTL` chunks present).
- `map-1-1.png` carries a debug colour tint and a per-supertile bright checkerboard.

## 9. Exterior tile group boundaries — RESOLVED from `plot_tile`

**Status:** Resolved. Derived from code; the ref prose has an off-by-one.

The exterior tileset uses a three-group sliding window selected by supertile index.
`TheGreatEscapeGraphics.ref` lines 203–205 and `TheGreatEscape.py:93` (`_tile()`) both assert a
grouping, but neither is traceable to an address, which §0 requires. `plot_tile` (`c$A9AD`)
states it directly:

```
$A9B0 LD BC,$8590   ; exterior_tiles[0]
$A9B3 CP $2D        ; 45
$A9B5 JR C,$A9C5    ;   supertile <  45        -> $8590
$A9B7 LD BC,$8A18   ; exterior_tiles[145]
$A9BA CP $8B        ; 139
$A9BC JR C,$A9C5    ;   supertile < 139        -> $8A18
$A9BE CP $CC        ; 204
$A9C0 JR NC,$A9C5   ;   supertile >= 204       -> $8A18
$A9C2 LD BC,$90F8   ; exterior_tiles[365]      -> otherwise (139..203)
```

| Supertile index | Base address | Tile number |
|---|---|---|
| 0–44 | `$8590` | 0 |
| 45–138 and 204–217 | `$8A18` | 145 |
| 139–203 | `$90F8` | **365** |

**Correction:** `TheGreatEscapeGraphics.ref` line 205 says the third group uses "tiles 366
onwards". It is **365**: `$90F8 − $8590 = $B68 = 2920`, and `2920 / 8 = 365`. The routine's own
comment table agrees ("use tiles 365..570"). The Python is correct because it uses the raw
address; only the ref prose is off by one. (Group 2 checks out: `$8A18 − $8590 = $488 = 1160`,
`1160 / 8 = 145`.)

The routine's comment also says "Supertiles 45..138 and 204..218", but there are only 218
supertiles (0..217), so the upper group is 204..217.

**Resolution:** implement the three comparisons exactly as `$A9B3`/`$A9BA`/`$A9BE` express them.
`map-0-0.png` remains the validation, since any banking error produces visibly wrong tiles.

## 10. Mask heights — RESOLVED; they are exactly derivable, not inferable

**Status:** Resolved. This also demotes the mask PNGs as an oracle.

The two RLE schemes differ: interior-object data carries a `width, height` header, but **mask
data carries only `width`**. `TheGreatEscape.py`'s `decode_masks()` therefore reconstructs
heights by scanning the usage tables (`exterior_mask_data` `$EC01` stride 8;
`interior_mask_data_source` `$EA7C` stride 7) and taking the worst-case bounding box per mask
reference — an inference, with mask 19 needing an explicit seed because nothing references it.

**That inference is unnecessary.** Height is exactly recoverable:

1. Read the 30 pointers from `mask_pointers` (`w$EBC5`).
2. **Sort them** — they are *not* stored in ascending order (entries 13, 14, 15, 17 are out of
   sequence, which is also why `Masks.html` lists them out of order).
3. Each mask's data extends to the next-higher pointer; the highest extends to `$EA7C`
   (`interior_mask_data_source`, where the mask data region ends).
4. `width` = first byte; expand the RLE from `ptr+1` to that extent; `height = expanded / width`.

I ran this over all 30 masks: **every one divides exactly**, with widths ranging 2–42. Given
those widths, exact division 30 times over is not a coincidence — the extents are right.

**The reference mask PNGs are therefore not a dimension oracle.** They encode the Python's
observed-usage bounding box, which differs from the stored data:

| Mask | Derived (true) | `mask-*.png` | Why they differ |
|---|---|---|---|
| `$E55F` | 42×26 | 42×25 | usage never exposes the last row |
| `$E99F` (index 19) | 9×5 | 9×1 | unused → inference has no data, falls back to the seed |
| `$E61E` | 16×16 | 16×16 | agree |
| `$E9CB` | 10×5 | 10×5 | agree |

**Resolution:** derive heights as above. Mask PNGs may still be compared pixel-wise *within
their own bounding box*, but must not gate mask dimensions — see `PLAN.md` §5, where they move
out of Tier 1 for that reason. Mask 19 is flagged explicitly in `data/` as unreferenced so its
absence from the reference build is visible rather than silent.

## 11. How map_position tracks the hero — RESOLVED

**Status:** Resolved. All three parts — the coordinate space, the scroll rule
and the initial value — now come from the disassembly.

**What I was reading:** `get_supertiles` (c$A7C9), the `shunt_map_*` family
(c$A9E4 onward), `hero_map_position` (`g$81B8`), and — the one that settled it —
`vischar_visible` (c$BAF7).

**Resolved: `map_position` is in ISO space, not world or tinypos space.**
`vischar_visible` compares it directly against `iso_pos.x / 8` on the horizontal
axis (`$BAFF`) and against `map_position.y * 8` in pixels on the vertical
(`$BB33`). The exterior map's tile grid *is* the isometric projection — the
artwork has the projection baked in — so a character is placed by projecting its
world position through `calc_vischar_iso_pos` and subtracting the window origin.

I originally derived `map_position` from the hero's tinypos in the P2 demo. That
is a different space, and it looked plausible only because both are "small
numbers of tiles". The correction is in `src/render/place.ts`, which states the
relationship explicitly so it cannot be re-guessed.

**Resolved: when to scroll.** `move_map` (c$AAB2) does not chase the hero at
all. The animation's own header names a direction to shunt, and a counter
`move_map_y` (`g$A7C6`) cycles 0..3 to spread one tile of travel across the four
frames of a walk cycle, filling the gaps with a sub-tile `game_window_offset`
(`g$A7C7`). Both are implemented in `ExteriorView.moveMap`.

Centring on the hero instead is what produced the visible jitter: the terrain
moved a whole tile while the hero moved two or four pixels.

**Resolved: the initial value.** `reset_outdoor_position` (c$B2FC), which
`transition` calls at `$68EF` whenever the hero ends up outdoors, sets it
outright:

    map_position.x = iso_pos.x / 8 - 11    ($B308..$B30D)
    map_position.y = iso_pos.y / 8 - 6     ($B314..$B319)

The constants differ because the units do: 11 is "the width of the game screen
minus half of the hero's width" in **bytes**, 6 is "the height ... minus half of
the hero's height" in **tile rows**. Halving the window on both axes — the
obvious guess, and what the demo did — gives 12 and 8, which is close enough to
look correct and wrong enough to misplace the hero. Both divisions are the
no-rounding form (`$E555`) and neither result is clamped to the map, so near an
edge the window genuinely runs off it.

This was found because the demo corrupted its own display: stepping outside left
`map_position` at the interior constant `(116, 234)`, and 234 is past the bottom
of a 136-row map, so the exterior renderer walked supertiles from nowhere. The
fix was not to clamp it but to call the routine the game calls.

## 12. The fourth byte of an animation header — RESOLVED

**Status:** Resolved during P3.

An animation is `{nframes, dirFrom, dirTo, mapDirection}`. The fourth byte is the
**map scroll direction**, read by `move_map` at `$AAC8`, with `255` meaning
"don't move" (`$AAC9`). That is why it is `255` for every turn and wait, and the
*opposite* direction for the four walks: "the map is shunted around in the
opposite direction to the apparent character motion."

Reversing an animation exchanges up and down by XORing the direction with 2
(`$AACC..$AAD0`).

## 13. Sprite placement uses the vischar rule, not the item rule — RESOLVED

**Status:** Resolved. This entry previously described a "phase dependency"
between the hero crossing a tile boundary and `move_map` firing its shunt, and a
compensation added to work around it. Both were wrong, and both are gone.

**What I was reading:** `setup_vischar_plotting` (`$E4D2..$E4F4`) versus
`setup_item_plotting` (`$DCA7..$DCBA`).

There are two placement routines and they differ on the vertical axis:

| | multiplier | granularity |
|---|---|---|
| Items (`$DCA7`) | `× 192` | 8 pixel rows — whole tiles |
| **Characters (`$E4ED`)** | **`× 24`** | **1 pixel row** |

24 bytes is one row of a 24-wide buffer. So characters are placed at PIXEL
granularity, from the full 16-bit `vischar.iso_pos.y`; only items are quantised
to tiles.

I had applied the item rule to the hero. That quantised him to 8-pixel vertical
steps, which the map scroll hides outdoors — where he holds a fixed screen
position — but which is plainly visible indoors, where nothing scrolls. Every
symptom traced back to it: the bouncing outdoors, the compensation that
appeared to fix it, and the bouncing indoors that the compensation could not
reach.

With the correct rule the sub-tile blit offset and the map shunt cancel exactly
and no compensation is needed. Measured: outdoors the hero's screen row is
constant while walking; indoors it moves a smooth two pixels per frame.

## §14 — What triggers a push is in the collision system, which is P4

**Read:** `setup_movable_items` (c$6939), the push logic at `$B071..$B0B8`, and its caller
`touch` (c$AF8F).

`$B071` is reached from `touch`, the routine that handles one vischar bumping into another. It
receives the pusher's direction already resolved and only decides where the item ends up; the
question of *whether* the hero is touching the stove at all is answered upstream, by the
bounding-box collision code that lands in **P4**.

The push logic itself is reproduced exactly (`src/game/movable.ts`, 18 tests). Only the trigger
is provisional: the demo uses proximity on both axes (within 6 units) as a stand-in, marked
`// ASSUMPTION:` at the call site in `src/main.ts`. It will be deleted when `touch` is
implemented — this is scaffolding for the demo, not a claim about the game.

One field worth flagging, because it reads as something it is not. The `movable_item` struct's
ninth byte is commented `byte index` and sits directly after the sprite pointer, which invites
reading it as a sprite selector. It is not — it is the vischar's **animation** index, and all
three movables store `0`. The sprite is chosen by the pointer at offset 6 (`$CE22` stove,
`$CE28` crate), which the extractor resolves to an index into the sprites array. Recorded as
`animIndex` so the two cannot be confused again.

## Not open, but worth recording

Two things that looked like problems and are not:

- **The `.skool` is a generated artifact** — it is in `.gitignore` (line 20) and is produced by
  `make skool` from `TheGreatEscape.ctl` + the pristine snapshot. This does not undermine §0's
  "sole source of truth", because all three representations agree by construction; and the
  extractor asserts exactly that by cross-checking its reconstructed image against
  `build/TheGreatEscape.pristine.z80`.
- **§3 says to parse `DEFB`/`DEFW`/`DEFM`** — there is no `DEFM` anywhere in the file. All five
  `t` (text) blocks use `DEFB` with the game's own glyph codes, in a charset that **skips the
  letter "O"** (digit zero doubles for it). No `DEFS` and no `s` blocks either.
